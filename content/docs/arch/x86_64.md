x86_64 is the production architecture: the one that boots to a desktop, drives real hardware, and runs
the full capsule fleet. Its `ArchOps` backend is a set of direct instruction sequences, and it owns the
x86-specific platform discovery. This page documents it. The code is under `src/arch/x86_64/`.

## The ArchOps implementation

The `X86_64` backend ([`src/arch/x86_64/abi.rs:26`](https://github.com/NON-OS/nonos-micro-kernel/blob/main/src/arch/x86_64/abi.rs#L26)) is a zero-sized type whose methods are single
instructions or short sequences:

```
  halt()                loop { cli; hlt }
  enable_interrupts()   sti
  disable_interrupts()  cli
  interrupts_enabled()  pushfq; pop; test RFLAGS bit 9 (IF)
  current_cpu_id()      CPUID leaf 1, EBX[31:24] -> local APIC id
  read_time_counter()   rdtsc -> EDX:EAX
  flush_tlb_one(addr)   invlpg [addr]
  switch_address_space  mov CR3, root
```

The CPU id is the local APIC id from CPUID, chosen because it is the identifier the platform IRQ
controller uses to route inter-processor interrupts, so the id the kernel sees matches the id the
hardware routes by. The time counter is `rdtsc`, the invariant timestamp counter that the
[clock](/docs/subsystems/time-and-clock/calibration/) calibrates to wall time elsewhere. Each method is
`#[inline(always)]` with tightly-scoped inline assembly, so the boundary adds no call overhead over
writing the instruction directly.

## The rest of the backend

The `ArchOps` impl is the leaf; the x86_64 tree under `src/arch/x86_64/` is much larger and holds the
arch-specific machinery the rest of the kernel's subsystems build on:

- the [GDT and TSS](/docs/subsystems/interrupts/idt/) with the IST stacks,
- the [syscall](/docs/subsystems/syscall/boundary/) `SYSCALL`/LSTAR entry,
- the [time](/docs/subsystems/time-and-clock/) TSC calibration (CPUID, PIT, HPET),
- the [interrupt](/docs/subsystems/interrupts/controllers/) IO-APIC and LAPIC,
- the FPU and SIMD setup,
- and the boot memory and framebuffer bring-up from the [handoff](/docs/subsystems/boot/handoff/).

These are documented with their subsystems; this page is the arch backend that sits beneath them.

## ACPI

x86_64 owns platform discovery through ACPI (`src/arch/x86_64/acpi/`). The ACPI module parses the
firmware tables and exposes the MADT, the HPET address, interrupt source overrides, the IO-APIC data,
the LAPIC address, NMI configurations, NUMA regions, PCIe segments, and the processor list. This is how
the kernel learns the machine's interrupt topology and processor inventory: the
[SMP](/docs/subsystems/smp/) bring-up reads the processor list to start the application processors,
and the [interrupt](/docs/subsystems/interrupts/controllers/) layer reads the IO-APIC and override data
to route device lines. On the other architectures this role is played by the flatspec
[device tree](/docs/arch/platform-discovery/) instead.

## Security analysis

The x86_64 backend is the most trusted arch code in the tree, because it is the one that actually runs
in production and because two of its `ArchOps` primitives are the hinges the rest of the kernel's
isolation hangs on. Three properties are worth stating plainly.

**The address-space switch is the isolation primitive.** `switch_address_space` writes CR3, and a CR3
write is what separates one capsule's private lower half from another's. The boundary contract requires
a valid root or the CPU faults, and the [scheduler](/docs/architecture/overview/) does not reach this
call blind: on the entry path it walks the target page-table root through the direct map and proves the
kernel halves, the user entry leaf, and the stack leaves before the switch, so a corrupt root is caught
by the pre-`iretq` audit rather than by a triple fault. The canonical boundary check in
[`arch/x86_64/context/setup.rs`](https://github.com/NON-OS/nonos-micro-kernel/blob/main/arch/x86_64/context/setup.rs) rejects any entry point or user stack above the non-canonical line before
a context is ever built. The backend provides the instruction; the layers above it provide the proof
that the operand is safe.

**The CPU id must match what the hardware routes by.** `current_cpu_id` returns the local APIC id from
CPUID leaf 1, not an arbitrary logical index, and this is a correctness property with a security edge:
the [interrupt](/docs/subsystems/interrupts/controllers/) layer and the
[hardware broker's](/docs/subsystems/hardware-broker/irq/) IRQ path route deliveries to APIC
destinations, so the id the kernel reasons about has to be the id the silicon delivers to. If these
diverged, an interrupt bound for the running CPU could be programmed to land on a core that never
services it, which is exactly the routing failure the IRQ page documents on real hardware.

**ACPI is attacker-adjacent firmware input.** The ACPI tables come from firmware, and the parser walks
them to learn the interrupt topology, the processor inventory, and the MMIO addresses the kernel will
later program. A malformed table is untrusted input reaching the kernel before any capsule runs, so the
parser is a hardening surface in its own right: it validates table structure rather than trusting
lengths and pointers, and the LAPIC and IO-APIC addresses it yields are only mapped into the upper half
during `init_unified_vm`, after the kernel half is confirmed, never as raw firmware pointers dereferenced
in place.

The remaining machinery this page points at (the GDT and its IST stacks, the `SYSCALL` entry, the FPU
setup) carries its own security story with its subsystem; this page is the arch leaf beneath them.

## Debugging

x86_64 backend faults tend to be low-level and early, before the log is fully up, so they are diagnosed
by symptom rather than by a returned error.

**Triple fault right after a context switch.** The usual cause is a bad page-table root or a user frame
that points into kernel space. Build with the `nonos-user-entry-proof` feature: the scheduler then walks
the target CR3 and prints `[USER-PROOF] FAIL ...` naming the leaf that did not validate (a missing
kernel half, an unmapped user RIP or RSP, a bad TSS.RSP0, or a missing PF/GP IST stack) and halts
instead of faulting blindly. That message localises the fault to a specific mapping.

**An MMIO write page faults during early init.** Programming the IO-APIC or touching the LAPIC before
`init_unified_vm` has remapped those pages into the upper half faults, because the window is not mappable
yet. The ordering fact in the [architecture overview](/docs/architecture/overview/) is the fix: IO-APIC
routing is initialised in `microkernel_init` after unified paging, not during early core init. A fault
here means an MMIO touch was hoisted ahead of the remap.

**An interrupt binds but never fires.** This is not an arch-backend bug; it is a routing or device-enable
state, and it is diagnosed on the [IRQ page](/docs/subsystems/hardware-broker/irq/). The one arch-backend
contribution to that failure is the CPU id: if `current_cpu_id` did not return the running core's APIC
id, a redirect aimed at "this CPU" would land elsewhere. On x86 it returns the APIC id from CPUID for
exactly this reason.

**A clock that does not advance or jumps.** `read_time_counter` is `rdtsc`, raw TSC ticks, not wall time.
Code that treats it as milliseconds will misbehave; wall-clock time comes from
[`sys::clock`](/docs/subsystems/time-and-clock/), which calibrates the TSC against the PIT and
HPET. A monotonic-but-wrong-rate clock points at the calibration, not at the backend.

## Source map

```
  src/arch/x86_64/abi.rs        the ArchOps backend (cli/hlt, sti, RFLAGS, CPUID, rdtsc, invlpg, CR3)
  src/arch/x86_64/acpi/mod.rs   the ACPI table parsing and accessors
  src/arch/x86_64/iommu/        the IOMMU support, compiled under the nonos-arch-iommu feature
  src/arch/x86_64/             the wider backend (GDT, syscall, time, interrupts, FPU, boot)
```

The `ArchOps` contract and the fail-to-link discipline are on the [boundary](/docs/arch/boundary/) page, the ACPI
side and its relationship to the device tree are on the [platform discovery](/docs/arch/platform-discovery/) page,
and the interrupt routing that consumes the CPU id is on the
[controllers](/docs/subsystems/interrupts/controllers/) page. Every reference above is verified against
`src/arch/x86_64/`.
